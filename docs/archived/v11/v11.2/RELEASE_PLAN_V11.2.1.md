# V11.2.1 Release Plan — Role-Based Workbench & Permission Governance

> AI量化交易闭环系统 — V11.2.1 规划说明  
> 文档版本：Draft v1.0 | 初稿日期：2026-03-15 | 状态：规划提案  
> 当前代码基线：V11.1.1 Trader Workbench Convergence & Architecture Simplification  
> 核心命题：**从“所有人看同一套复杂系统”升级为“按角色提供清爽工作台、清晰功能边界、最小必要权限和稳定治理”的下一阶段平台化演进。**

---

## 0. 版本定位

### 0.1 一句话定义

V11.2.1 是一次 **Role-Based Workbench & Permission Governance** 升级：

> 让系统从“功能强但入口过多、信息密度对所有人一视同仁”的统一控制台，演进为一套**按角色裁剪视图、按职责授予动作、按边界组织页面与接口**的交易平台。

### 0.2 为什么是 V11.2.1

V11.1.1 已经完成了工作台收敛的第一步：

- 三个核心工作台统一使用 `WorkbenchShell` 与 `ExplainabilityStrip`；
- 后端开始通过 `read_models/` 提供聚合读模型；
- `/task-management` 已收口到 `/system-monitor` 的 tasks tab；
- 前后端开始围绕稳定 DTO 和 thin router 演进。

但 V11.1.1 仍然存在一个非常现实的问题：

- 系统页面很多，且对不同角色暴露的复杂度基本相同；
- 当前认证仍以**单管理员账号**为主，缺少正式用户体系；
- 前端当前主要是“是否登录”级别的路由守卫，还没有角色级菜单与按钮裁剪；
- 后端只有少数接口存在局部权限判断，缺少统一 RBAC（Role-Based Access Control）框架；
- 研究、交易、管理、汇报四类人群被迫共享同一套信息结构，导致认知负担和误操作风险上升。

因此，V11.2.1 不再优先扩功能，而是优先回答：

- **谁应该看到哪些页面？**
- **谁可以点击哪些按钮？**
- **谁能访问哪些接口与数据？**
- **如何让研究员、交易员、主管、管理员各自只面对“自己该面对的系统”？**

### 0.3 当前现实诊断（基于现有代码结构）

当前系统的权限与身份能力还停留在早期阶段：

1. **后端认证仍是单管理员模型**  
   `app/core/auth.py` 当前仅校验 `settings.ADMIN_USERNAME / ADMIN_PASSWORD`，JWT 主要只携带 `sub`，尚未形成正式用户实体、角色模型与权限声明。

2. **前端当前只有登录态守卫，没有角色态守卫**  
   `src/router/index.ts` 当前按 `isLoggedIn()` 控制是否可访问页面，但没有基于角色的路由元信息过滤、导航裁剪和按钮隐藏策略。

3. **局部接口已出现“权限需求”，但实现是散点式的**  
   `app/routers/strategy.py` 目前通过 `STRATEGY_EXECUTE_USERS / STRATEGY_MANAGE_USERS` 进行局部动作限制，这说明系统已经天然需要权限治理，但还没有统一抽象。

4. **当前信息架构已经具备收敛基础**  
   V11.1.1 已将多个关键页面纳入 workbench shell/read model 模式，这为 V11.2.1 按角色继续做“工作台裁剪”提供了良好支点，而不是推倒重来。

### 0.4 V11.2.1 不可妥协的边界

1. **不能只做前端隐藏**：所有页面、按钮与动作权限都必须以**后端授权**为最终真源。  
2. **不能放宽交易与风控纪律**：角色权限的引入不能成为绕过 RiskGate、治理门或自动执行主链的捷径。  
3. **不能破坏 V11.1.1 的 workbench 收敛方向**：新角色体验应建立在现有共享 shell / read model 之上，而不是再造平行页面体系。  
4. **不能让管理员成为“无审计超人”**：管理员拥有广泛权限，但越权查看、代操作、角色分配与紧急授权必须有审计证据。  
5. **不能把权限逻辑散落在几十个页面里**：V11.2.1 必须建立统一的角色、权限、路由、按钮、数据范围抽象。

## 1. 顶层目标

### 1.1 版本总目标

V11.2.1 的目标不是简单增加“用户管理功能”，而是完成以下四件事：

- 建立正式的**用户—角色—权限**模型；
- 为四类角色提供**清爽、聚焦、低打扰**的专属工作台入口；
- 将页面权限、按钮权限、接口权限、数据权限统一到同一套治理框架；
- 在不破坏交易主链和治理纪律的前提下，把系统从“单人超级控制台”升级为“多角色协同平台”。

### 1.2 四条设计原则

| 原则 | 含义 | 对应要求 |
| ---- | ---- | -------- |
| 最小必要权限 | 每个角色只获得完成职责所需的最小能力 | 默认拒绝，按需开放 |
| 角色优先体验 | 先定义角色工作目标，再定义页面和按钮 | 不让用户自己在复杂导航中找路 |
| 后端授权为真源 | 前端负责裁剪体验，后端负责最终裁决 | 禁止仅靠 UI 隐藏做安全 |
| 共享骨架而非平行复制 | 角色工作台建立在现有 workbench/read model 之上 | 不新增四套完全平行页面 |

### 1.3 成功标准

| 维度 | 当前问题 | V11.2.1 目标 | 验收方式 |
| ---- | -------- | ------------ | -------- |
| 身份模型 | 单管理员登录 | 支持正式用户与角色体系 | 后端 schema / API 验收 |
| 页面暴露 | 登录后近乎全量暴露 | 按角色动态裁剪导航与首页 | 角色登录验收 |
| 按钮暴露 | 大量动作默认可见 | 关键动作按权限显示/禁用/解释 | UI 验收 |
| 接口授权 | 局部白名单、无统一抽象 | 关键业务接口统一接入 RBAC | 接口测试 |
| 数据边界 | 同一页面信息过载 | 角色读模型按职责聚合 | read model / DTO 验收 |
| 管理能力 | 无正式用户/角色分配面板 | 管理员可管理用户、角色、授权与审计 | 管理后台验收 |

## 2. 角色体系定义

V11.2.1 引入四个一等角色：

1. **研究员（Researcher）**
2. **交易员（Trader）**
3. **主管（Supervisor）**
4. **管理员（Administrator）**

> 说明：V11.2.1 默认采用“单角色主归属”模式，避免初版就进入复杂多角色叠加。若确有需要，可在后续版本扩展为多角色组合，但初版应以清晰优先。

### 2.1 研究员（Researcher）

#### 研究员角色目标

专注于**信号产生、研究分析、策略验证、机会筛选、研究证据链**，不进入真实交易动作发起与执行流程。

#### 研究员权限边界

- **可做**：
  - 运行研究与扫描；
  - 查看候选信号、研究结论、体制判断、事件背景与回测结果；
  - 管理策略参数、研究配置、研究结果导出；
  - 查看“为什么产生这个候选信号”。
- **不可做**：
  - 发起快捷交易、批量交易、下单、改单、撤单；
  - 触发真实执行路径；
  - 修改执行策略、风控阈值、系统任务、用户权限。

#### 研究员推荐工作台

**Research Workbench** —— 面向“研究结论形成但尚未进入交易触发”这一边界。

#### 研究员典型页面范围

- `/alpha-lab`
- `/opportunities`
- `/macro`
- `/regime`
- `/events`
- `/strategies`
- `/strategies/:id`
- `/backtest`
- `/etf-pool`
- `/options`
- `/signal-watchtower`（只读研究视角）
- `/observability/signal`（只读研究视角）

### 2.2 交易员（Trader）

#### 交易员角色目标

专注于**交易动作、执行质量、持仓生命周期、订单解释、执行后审计**。

#### 交易员权限边界

- **可做**：
  - 查看订单簿、执行策略、交易生命周期、持仓与持仓评估；
  - 发起受控交易动作（前提是仍通过 RiskGate / AutonomousEngine / execution policy）；
  - 调整执行相关参数、查看执行成本与执行后归因；
  - 跟踪交易卡点与异常。
- **不可做**：
  - 管理研究策略库结构与研究员工作台配置；
  - 分配用户角色；
  - 修改系统任务编排、平台权限模型与全局治理开关。

#### 交易员推荐工作台

**Trading Workbench** —— 面向“从交易触发到持仓与执行后回放”的主链控制台。

#### 交易员典型页面范围

- `/order-book`
- `/execution-policy`
- `/trade-lifecycle`
- `/positions`
- `/position-evaluation`
- `/paper`
- `/journal`
- `/attribution`
- `/observability/execution`
- `/observability/risk`
- `/alerts`

### 2.3 主管（Supervisor）

#### 主管角色目标

只关注**收益、回撤、风险、执行质量总览、系统风险、关键经营结果**，强调报表和摘要，而不是过程操作。

#### 主管权限边界

- **可做**：
  - 查看收益、风险、容量效率、重大风险、执行质量和结果归因；
  - 查看经营报表、日报/周报、风险概览、关键异常清单；
  - 查看建议动作与升级信号。
- **不可做**：
  - 直接发起研究任务、执行交易或修改系统任务；
  - 进入过多实现细节、配置细节和平台级运维能力。

#### 主管推荐工作台

**Executive Workbench** —— “少页面、高摘要、重报表”的高管视角。

#### 主管典型页面范围

- `/dashboard`（主管裁剪版）
- `/war-room`（主管摘要版，可选）
- 新增建议：`/reports/executive`
- 新增建议：`/reports/risk`
- 新增建议：`/reports/performance`
- `/autonomy`（仅摘要与解释视角，隐藏控制动作）
- `/portfolio`（只读结果视角，非研究配置视角）

### 2.4 管理员（Administrator）

#### 管理员角色目标

专注于**系统监控、任务管理、用户管理、角色权限分配、平台治理、运行可靠性与平台级智能辅助**。

#### 管理员权限边界

- **可做**：
  - 管理用户、角色、权限模板；
  - 查看系统监控、任务运行、作业健康、服务拓扑；
  - 进行授权分配、账号启停、任务补跑、平台级设置治理；
  - 查看权限审计、访问拒绝日志与角色配置差异。
- **谨慎可做**：
  - 只读跨域查看研究/交易/主管页面，用于排障；
  - 紧急托管操作（需审计）。
- **默认不鼓励**：
  - 以管理员身份承担日常研究或交易工作。

#### 管理员推荐工作台

**Admin Workbench** —— 面向系统与平台治理，而不是交易主链操作。

#### 管理员典型页面范围

- `/system-monitor`
- `/task-management`
- 新增建议：`/admin/users`
- 新增建议：`/admin/roles`
- 新增建议：`/admin/permissions`
- 新增建议：`/admin/audit`
- `/copilot`（平台治理助理模式）

### 3.4 数据边界

V11.2.1 不仅要裁页面和按钮，还要裁**数据密度和数据范围**：

- 研究员看到的是研究输入、候选信号、研究证据，不出现真实交易控制按钮；
- 交易员看到的是交易对象、执行状态、风险拦截原因、执行后结果；
- 主管看到的是报表、趋势、收益风险摘要，不展示实现细节和配置噪声；
- 管理员看到的是平台状态、作业、权限和审计，不默认进入交易细节。

这意味着同一底层数据不必在所有角色首页以相同结构暴露，而应通过**角色 read model** 做聚合裁剪。

## 4. 前端规划（Role-Based Experience）

### 4.1 目标

让前端从“统一导航 + 登录态守卫”升级为“角色首页 + 角色导航 + 角色按钮 + 角色状态语言”。

### 4.2 核心能力

#### 1. 角色感知认证状态

新增统一认证状态模型：

- 当前用户基础信息
- 当前角色编码
- 当前权限集合
- token 过期时间
- 权限版本号（便于服务端失效控制）

建议新增：

- `src/stores/auth.ts`
- `src/types/auth.ts`
- `useAuthz()` / `usePermission()` 组合式函数

#### 2. 路由元信息权限化

当前 `src/router/index.ts` 只有登录态控制；V11.2.1 需要为路由增加：

- `meta.roles`
- `meta.permissions`
- `meta.accessMode`（standard / readonly / summary）
- `meta.workbenchDomain`

并实现：

- 未登录 → 跳登录页
- 已登录但无权限 → 跳角色首页或 `403` 页面
- 角色不匹配 → 不渲染菜单，不暴露直链入口

#### 3. 角色导航裁剪

侧边导航和首页推荐入口必须按角色动态生成：

- 研究员只看到研究相关导航；
- 交易员只看到执行与持仓相关导航；
- 主管只看到报表与风险摘要入口；
- 管理员只看到平台与用户权限入口。

目标不是让用户“自己学会忽略不相关菜单”，而是让系统先帮用户做好裁剪。

#### 4. 按钮权限组件化

新增统一能力：

- `PermissionButton`
- `PermissionGuard`
- `v-can` 指令或等价组合式方案

用于管理：

- 显示 / 隐藏
- 禁用 / 可点击
- 权限不足提示
- 审计上下文透传（如需）

#### 5. 角色首页与工作台入口

建议新增四个角色首页入口：

- `ResearchHomePage.vue`
- `TradingHomePage.vue`
- `ExecutiveHomePage.vue`
- `AdminHomePage.vue`

这些页面不应复制现有所有功能，而应利用：

- `WorkbenchShell`
- `ExplainabilityStrip`
- role-specific summary cards
- role-specific quick actions

形成更聚焦的日常入口。

#### 6. 403 / 无权限体验

新增明确状态页：

- 未授权访问页面时显示“你当前角色无此权限”；
- 给出返回角色首页的快捷动作；
- 不显示技术错误或空白页。

### 4.3 前端验收标准

- [ ] 登录后导航根据角色动态裁剪
- [ ] 核心路由具备角色守卫与无权限兜底页
- [ ] 关键按钮实现统一权限控制，不再散落 `if` 判断
- [ ] 四个角色均具备专属首页入口
- [ ] 主管视角能以少页面方式看到收益/风险/报表核心信息
- [ ] 前端权限控制与后端权限结果一致，不出现“前端可点、后端必拒”大面积体验断裂

## 5. 后端规划（RBAC & Authorization）

### 5.1 目标

让后端从“单管理员认证 + 个别接口白名单”升级为正式的 RBAC 授权体系。

### 5.2 核心能力

#### 1. 用户与角色数据模型

建议新增核心实体：

- `User`
- `Role`
- `Permission`
- `UserRoleBinding`
- `RolePermissionGrant`
- `AuthorizationAuditLog`

建议支持的基础字段：

- 用户：用户名、展示名、状态、密码哈希、默认角色、最后登录时间
- 角色：编码、名称、描述、是否系统内置
- 权限：资源、动作、范围、说明
- 绑定关系：生效状态、创建人、更新时间

#### 2. JWT 声明升级

当前 JWT 主要只带 `sub`；V11.2.1 建议携带：

- `sub`
- `uid`
- `role`
- `permissions_version`
- `display_name`
- `exp`

必要时可考虑：

- `scopes`
- `readonly_overrides`

目标是让前端能快速完成体验裁剪，同时保留后端真源校验。

#### 3. 统一授权依赖

新增统一授权依赖与装饰器，而不是继续在各 router 内手写判断：

- `require_role(...)`
- `require_any_role(...)`
- `require_permission(resource, action)`
- `require_access_mode(summary|readonly|write)`

适用对象：

- router 级
- endpoint 级
- 部分 service 级二次校验

#### 4. 资源—动作权限模型

建议以“资源 + 动作”方式组织权限，例如：

- `research.strategy.read`
- `research.strategy.manage`
- `research.signal.read`
- `trading.order.execute`
- `trading.execution_policy.manage`
- `report.performance.read`
- `admin.user.manage`
- `admin.role.assign`
- `admin.task.operate`
- `admin.system.read`

首版不建议一开始做过细字段级权限，而应先覆盖：

- 页面入口级
- 关键写动作级
- 高风险接口级
- 管理能力级

#### 5. 角色 read model

延续 V11.1.1 的 read model 模式，建议新增：

- `app/services/read_models/research_home.py`
- `app/services/read_models/trading_home.py`
- `app/services/read_models/executive_reports.py`
- `app/services/read_models/admin_overview.py`

角色首页优先读聚合接口，而不是前端自己拼多请求。

#### 6. 权限审计

V11.2.1 需要把权限体系纳入审计：

- 角色分配谁做的
- 关键授权变更何时发生
- 哪个用户访问了被拒绝资源
- 管理员是否执行了紧急托管动作

#### 7. 种子用户初始化（Seed Users Bootstrap）

RBAC 体系上线后，系统必须在首次部署或 migration 完成时自动初始化四个内置种子用户，每个用户绑定对应角色，确保系统可立刻以四种角色身份登录验收，无需依赖手工创建流程。

| 用户名 | 默认角色 | 说明 |
| ------ | -------- | ---- |
| `researcher` | Researcher | 研究员种子账号，绑定研究员角色 |
| `trader` | Trader | 交易员种子账号，绑定交易员角色 |
| `supervisor` | Supervisor | 主管种子账号，绑定主管角色 |
| `admin` | Administrator | 管理员种子账号，绑定管理员角色 |

要求：

- 种子用户密码**必须通过环境变量注入**（如 `SEED_RESEARCHER_PASSWORD`、`SEED_TRADER_PASSWORD` 等），不得硬编码在代码或迁移脚本中；
- 种子用户应标记为系统内置（`is_system_seed=True`），防止被误删或角色解绑；
- 初始化逻辑建议放在 `scripts/bootstrap/` 目录下或 Alembic 数据 migration 中，与 schema migration 解耦；
- 每次初始化前先检测是否已存在，保证幂等，可安全重复执行；
- 登录首次使用时应提示修改密码（可选，首版建议记录在运维说明中）。

### 5.3 后端接口规划（建议）

#### 身份与授权

- `POST /api/v1/auth/login`
- `POST /api/v1/auth/logout`
- `GET /api/v1/auth/me`
- `GET /api/v1/auth/permissions`

#### 管理员接口

- `GET /api/v1/admin/users`
- `POST /api/v1/admin/users`
- `PATCH /api/v1/admin/users/{user_id}`
- `POST /api/v1/admin/users/{user_id}/roles`
- `GET /api/v1/admin/roles`
- `POST /api/v1/admin/roles`
- `PATCH /api/v1/admin/roles/{role_id}`
- `GET /api/v1/admin/permissions`
- `GET /api/v1/admin/audit/authz`

#### 角色首页/报表

- `GET /api/v1/research/home`
- `GET /api/v1/trading/home`
- `GET /api/v1/executive/summary`
- `GET /api/v1/executive/risk-report`
- `GET /api/v1/admin/overview`

### 5.4 后端验收标准

- [ ] 支持正式用户与角色模型，不再依赖单管理员账号模型
- [ ] JWT 声明可表达角色与权限版本
- [ ] 关键接口统一接入授权依赖
- [ ] 研究、交易、主管、管理员四类角色具备明确接口边界
- [ ] 管理员可管理用户、角色和授权，并可查看授权审计
- [ ] 所有高风险写操作都有明确权限检查和拒绝日志
- [ ] 系统部署后自动完成四个种子用户初始化（`researcher` / `trader` / `supervisor` / `admin`），各绑定对应角色，密码由环境变量注入，无硬编码

## 6. 角色工作台信息架构

### 6.1 研究员工作台（Research Workbench）

#### 研究员工作台要回答的问题

- 今天哪些标的/策略值得研究？
- 候选信号从何而来？
- 为什么这个信号分数高或低？
- 哪些策略值得继续跑，哪些需要回测验证？

#### 研究员工作台首页结构建议

- 今日研究摘要
- 高潜候选清单
- 策略运行状态
- 体制/事件背景摘要
- 研究任务建议动作

### 6.2 交易员工作台（Trading Workbench）

#### 交易员工作台要回答的问题

- 现在有哪些订单/执行对象在进行？
- 为什么被缩量、延迟、拒绝或降级？
- 当前持仓需要调整什么？
- 哪些交易异常需要我立刻处理？

#### 交易员工作台首页结构建议

- 活跃订单与生命周期摘要
- 风险卡点与执行卡点
- 持仓风险与执行质量摘要
- 待人工处理动作

### 6.3 主管工作台（Executive Workbench）

#### 主管工作台要回答的问题

- 当前收益表现如何？
- 风险水位是否安全？
- 哪些问题正在拖累收益或放大风险？
- 系统是否稳定运行，是否需要升级关注？

#### 主管工作台首页结构建议

- 收益总览（日报/周报/月度）
- 风险总览（VaR、回撤、相关性、容量摩擦）
- 执行质量摘要
- 核心异常与建议动作
- 报表导出入口

### 6.4 管理员工作台（Admin Workbench）

#### 管理员工作台要回答的问题

- 系统健康是否正常？
- 哪些任务失败、延迟或需要补跑？
- 当前用户和角色分配是否正确？
- 是否存在越权访问、频繁拒绝或配置漂移？

#### 管理员工作台首页结构建议

- 平台健康与作业摘要
- 用户与角色状态
- 权限变更与拒绝日志
- 系统治理建议动作

## 9. 统一验收矩阵

### 9.1 产品体验

- [ ] 四类角色登录后都只看到与自身职责一致的主导航
- [ ] 四类角色均具备专属首页或专属工作台入口
- [ ] 主管视角显著简化为报表与核心风险摘要，不再暴露大量过程操作
- [ ] 页面和按钮权限能显著降低认知噪声与误触发风险

### 9.2 前端架构

- [ ] 路由、菜单、按钮三层权限控制统一抽象
- [ ] 权限不足有清晰兜底页与说明
- [ ] 角色工作台继续复用 `WorkbenchShell` / `ExplainabilityStrip`
- [ ] 不新增四套完全平行的大页面体系

### 9.3 后端架构

- [ ] 用户—角色—权限模型正式落地
- [ ] 关键接口统一采用授权依赖而非散点 if 判断
- [ ] 角色首页通过 read model 提供聚合数据
- [ ] 授权拒绝、角色变更、紧急托管具备审计证据
- [ ] 可分别以 `researcher` / `trader` / `supervisor` / `admin` 四个种子用户登录，并验证各自角色权限与工作台体验一致

### 9.4 风险与治理

- [ ] 权限系统不会绕过 AutonomousEngine、RiskGate、治理门与执行纪律
- [ ] 前后端权限口径一致
- [ ] 管理员高权限动作可追溯
- [ ] 不因角色引入而放宽任何交易安全边界

## 10. 非目标（明确边界）

V11.2.1 当前不以以下事项为主目标：

1. 重写整套前端导航系统或组件库
2. 一次性完成字段级/行级/组织级极细粒度权限
3. 把四个角色扩展为十几个岗位体系
4. 借权限治理之名重做交易主链
5. 为了“管理方便”让管理员无审计跨域操作一切

---

## 11. 最终判断

V11.2.1 的价值不在于“加了用户管理”，而在于：

- 让**研究员**终于只面对研究与信号链路；
- 让**交易员**终于只面对交易与执行主链；
- 让**主管**终于只面对收益、风险与经营结果；
- 让**管理员**终于只面对平台治理、任务、用户和授权。

如果说：

- **V11.1.1** 的关键价值，是把系统从页面堆叠推进到工作台收敛；
- 那么 **V11.2.1** 的关键价值，就是把这套工作台真正变成一套**按职责组织、按边界授予、按角色呈现**的平台。

这会让系统不只是“能做很多事”，而是开始具备顶级平台应有的三个特征：

> **看得清、管得住、用得对。**
